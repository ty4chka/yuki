# yuki: модель безопасности и обновлений

yuki ставит приложения в систему (`sudo yuki install`) и библиотеки в проекты (`yuki add`).
Своих серверов нет: реестр это git-репозиторий, файлы раздаёт GitHub/Codeberg/GitLab.
Доверие строится на подписях и хешах, а не на хостинге.

## 1. От чего защищаемся

| Угроза | Чем закрыта |
|---|---|
| Подмена архива на хостинге или в CDN | blake3 в подписанной записи индекса; root проверяет повторно |
| Подмена самого индекса | Ed25519-подпись записи, ключи только из `/etc/yuki/trusted_keys` |
| Откат на старую уязвимую версию | `seq` в записи + локальное состояние `seen` (пишет только root) |
| «Замороженный» индекс | `expires`: просроченная запись отвергается |
| Тихая замена опубликованной версии | `update` падает, если у той же версии сменился хеш |
| Вредный архив (`../`, симлинки, setuid, zip-бомба) | `audit_tar` до распаковки + policy + лимиты размера |
| Пакет пишет туда, куда не должен | policy: только `usr/ opt/ etc/`, чёрный список (sudoers, pam, ssh, CA, `etc/yuki`, ядро) |
| Чужой пакет подменяет `yuki` | путь `usr/bin/yuki*` разрешён только пакету `yuki` |
| Компрометация сети/сборки поднимает root | разделение привилегий (см. п. 3) |
| Вредный билд-скрипт | сборка в bubblewrap без сети, команда и список файлов из подписанной записи |
| Сбой посреди установки | журнал транзакции и откат в обратном порядке, блокировка |
| Утёкший ключ реестра | отзыв и ротация, подписанные порогом ключей |

## 2. Цепочка доверия

1. В клиент вручную добавлен ключ реестра (`yuki keys trust`, отпечаток подтверждает человек).
2. Ключ подписывает запись пакета: `"yuki-v1\n" + байты файла` (доменный разделитель).
3. Запись содержит URL и `blake3:` архива для каждой платформы (или исходники).
4. Архив проверяется по хешу, затем аудит, затем policy, затем хеш каждого файла.
5. В базе (`/var/lib/yuki/db`) остаются хеши всех установленных файлов: `yuki check`.

## 3. Разделение привилегий (как у pacman с DownloadUser, но жёстче)

Запуск `sudo yuki install foo` делает пять шагов:

1. **Ребёнок** (`fork`, затем `setgroups(0)`, `setgid`, `setuid(nobody)`, проверка, что root не вернуть, `no_new_privs`) приносит записи индекса.
2. **Root** заново проверяет подписи, срок, откат и сам строит план. Ничего из ответа ребёнка не принимается на веру.
3. **Ребёнок** скачивает архивы или собирает из исходников в песочнице.
4. **Root** убивает все процессы nobody (чтобы демон не менял файлы дальше), копирует артефакты к себе
   (только обычные файлы, без симлинков), снова проверяет blake3 и аудит, распаковывает в каталог root.
5. **Root** применяет транзакцию.

Состояние анти-отката `seen` пишет только root. Ребёнок его только читает.

## 4. Сборка из исходников

* Выбирается, только если для платформы нет готовой сборки.
* Всегда отдельный вопрос `Build X from source? [y/N]`. `--yes` его не заменяет, нужен явный `--allow-build`.
* Показываются команда сборки, число пакуемых файлов, доступ к сети и режим песочницы.
* bubblewrap: `--unshare-all` (в т.ч. сеть), корень только для чтения, `/tmp` в памяти, писать можно только в каталог сборки,
  таймаут 30 минут. Сеть включается только если запись индекса явно разрешает (`"net": true`) и это видно в плане.
* Нет bubblewrap: сборка отклоняется, пока админ не создал `/etc/yuki/allow_unsandboxed_build`.
* В систему попадают только файлы из списка `files` в подписанной записи (`from → to, mode`), а не всё, что создал скрипт.
* Для сборки из исходников хеш результата подписать нечем: доверие идёт к исходникам и песочнице. В базе пакет помечен `origin=source`.

## 5. Обновления

* `sudo yuki upgrade [pkg]`: запрос индекса, таблица `старая → новая`, одно подтверждение, затем обычная транзакция на пакет.
* Конфиги в `etc/`: если пользователь менял файл, новый ложится рядом как `.yuki-new`, пользовательский не трогается.
* **Обновление самого yuki** это обычный пакет `yuki`. После применения запускается `/usr/bin/yuki version`;
  если новый бинарник не стартует, транзакция откатывается автоматически.
* `sudo yuki rollback [id]` откатывает последнюю транзакцию по журналу (файлы, каталоги, запись в базе).
* `sudo yuki sys-audit` находит установленные версии, которые сняты с индекса (yanked).

## 6. Ключи: ротация и отзыв

* `keys/rotation.json` + `keys/rotation.sigs` в индексе. `sudo yuki keys refresh` применяет файл, только если его подписали
  не меньше `threshold` разных уже доверенных ключей (`/etc/yuki/threshold`, рекомендуется 2 из 3).
* Новый ключ не может ввести сам себя. Отозванный ключ уходит в `revoked_keys` и не вернётся.
* Рекомендуется держать корневые ключи офлайн, а ключ CI, который продлевает `expires` (`yuki renew`), сделать отдельным.

## 7. Роли ключей и подтверждение содержимого

* Ключ в `trusted_keys` имеет роль: `publisher` (по умолчанию) или `renewer`.
* В записи есть `content_sigs`: подписи издателей над списком релизов. Клиент требует не меньше `publish_threshold`
  РАЗНЫХ издателей (файл `/etc/yuki/publish_threshold`, по умолчанию 1, для публичного реестра советуем 2).
* `renewer` может подписать обёртку записи (срок, `seq`), но не содержимое. Поэтому ключ автопродления в CI не может подсунуть
  свой релиз: без подписей издателей на `versions` запись отвергается.
* `yuki index cosign <pkg> <key>` добавляет подпись второго издателя; `yank` и `publish` меняют содержимое и требуют новых подписей.

## 8. Параллельные загрузки, сборки и отказоустойчивость

* Скачивание идёт пулом потоков (по умолчанию до 4, `YUKI_JOBS=1..16`). Воркер сам качает, сверяет хеш и пишет прогресс в файл,
  а рисует один главный поток, поэтому панель не замирает во время хеширования. Данные между потоками не разделяются.
* Разбор chunked и повторные редиректы поддержаны, иначе загрузчик падал бы на «неудобных» серверах.
* `install a b c` и `upgrade` строят один общий план и применяются ОДНОЙ транзакцией.
* Журнал целиком пишется до первого изменения и сбрасывается на диск (`sync`); незавершённая транзакция после сбоя питания
  откатывается автоматически при следующем запуске.
* Безопасные симлинки разрешены: цель относительная, без `..` за пределы `usr/`, `opt/`, `etc/`, список берётся из аудированного архива.
* Сборка из исходников: если в записи у файла указан `blake3`, результат сверяется с подписанным хешем и в песочнице, и ещё раз в root.
  Без хеша сборку нельзя проверить, и yuki прямо об этом предупреждает.
* Платформа приводится к одному виду (`amd64` → `x86_64`, `arm64` → `aarch64`), `YUKI_TARGET` переопределяет.
* Общие зависимости проектов учитываются по владельцам: `yuki remove` убирает только то, что больше никому не нужно.
* Индекс можно указать несколькими зеркалами (`YUKI_INDEX=url1,url2`): подписи проверяются те же, доверия зеркалу не нужно.
* `yuki selftest` проверяет собранный бинарник на эталонах (blake3, Ed25519, политика, JSON, потоки).

## 9. Что не защищено (честно)

* Компрометация нужного числа ключей издателей: подписанный вредный релиз установится. Помогают порог 2 из 3 и офлайн-ключи.
* Сборка без хешей в записи: песочница снижает риск, но не доказывает соответствие исходникам.
* Побег из bubblewrap или уязвимость ядра.
* Скачивание идёт по HTTPS с проверкой сертификатов, но yuki не закрепляет сертификаты хостов (и не должен: целостность держится на подписях).
* Код не компилировался на реальной машине; запустите `yuki selftest` сразу после сборки.

## 10. Эксплуатация индекса

* Репозиторий `yuki-index`: PR-ы с проверкой CI (скачать, сверить blake3, `yuki inspect`, проверить `deps`), подпись коммитов.
* Подписывает `yuki publish` на машине мейнтейнера или в защищённом CI; `renew` по расписанию продлевает `expires`.
* В `.gitattributes`: `* -text`, иначе перевод строк сломает подписи.
